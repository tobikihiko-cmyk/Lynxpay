# LynxPay failure and load test matrix

Run disruptive scenarios only against the disposable E2E or staging environment.
Every load command writes JSON and Markdown under `artifacts/performance`; outage
drills write JSON under `artifacts/failure`.

## Automated scenarios

| Scenario | Tool | Release gate |
| --- | --- | --- |
| Health/read load | `python3 tests/load/lynxpay_load.py --scenario ready --requests 1000 --concurrency 50` | 0 failures, p95 within threshold |
| Authenticated payment reads | `python3 tests/load/lynxpay_load.py --scenario payments-read --token "$TOKEN"` | 0 failures, p95 within threshold |
| Callback burst | `python3 tests/load/lynxpay_load.py --scenario callback-burst --merchant-id "$MERCHANT_ID" --callback-payload tests/load/examples/mpesa-callback.json --allow-writes` | All callbacks durably acknowledged; backlog drains |
| Duplicate callbacks | Use the previous command with `--scenario duplicate-callback` | One state transition; duplicates retained as evidence |
| Concurrent sandbox STK | `python3 tests/load/lynxpay_load.py --scenario concurrent-stk --token "$TOKEN" --stk-payload tests/load/examples/stk-sandbox.json --allow-writes` | Unique intentions and idempotent retries; no double prompts |
| Redis outage | `python3 tests/failure/run_outage_scenario.py redis-outage --token "$TOKEN" --allow-disruption` | Authenticated API fails closed, then recovers |
| Worker crash | `python3 tests/failure/run_outage_scenario.py worker-crash --allow-disruption` | Lease recovery and healthy heartbeat within 60 seconds |
| Slow/failed Safaricom | `pytest -q tests/test_core.py::test_stk_uncertain_transport_becomes_unknown` | Payment becomes `unknown`, never false `failed` |
| Slow merchant webhook | `pytest -q tests/test_phase2.py::test_webhook_retry_then_dead_letters` | Bounded timeout, retry, then dead letter |
| Concurrent callbacks | `pytest -q tests/test_postgres_concurrency.py::test_simultaneous_success_callbacks_transition_once` | Exactly one success transition |
| Cross-tenant RLS | `pytest -q tests/test_postgres_concurrency.py::test_rls_hides_and_blocks_cross_tenant_rows_for_non_owner_role` | Tenant B cannot read or write tenant A |
| Reconciliation race | `pytest -q tests/test_v2_payment_correctness.py::test_callback_success_wins_while_reconciliation_network_call_is_in_flight` | Provider callback wins without status regression |

## Deployment-level drills

Run these manually in staging because they require provider and infrastructure
controls that unit tests cannot faithfully simulate:

1. Cap the PgBouncer pool at the staging connection limit, run the read probe at
   increasing concurrency, and confirm bounded 503/timeout behavior rather than
   process crashes. Capture Render database and `lynxpay_database_pool_*` graphs.
2. Add 500 synthetic `unknown` sandbox payments, pause reconciliation workers for
   five minutes, restore workers, and measure drain time and oldest-item age.
3. Keep callback and read probes running while deploying the API. Confirm at
   least one healthy instance remains available and every callback is retained.
4. Scale API and webhook workers to two replicas. Repeat duplicate callback and
   webhook retry tests and verify exactly-once state transitions through database
   locking and leases.
5. Apply provider latency and connection resets through the staging network
   proxy. Verify `unknown` outcomes, reconciliation recovery, and no automatic
   retry that can double-prompt a customer.

The release owner attaches generated reports, screenshots, and any accepted
deviations to the release evidence generated by `ops/release_evidence.py`.
